## Implemented workflow

1. Account → Privacy & Account → Delete My Account explains active listing/file/dispute consequences and that this is human review, not immediate erasure or suspension. The email/WhatsApp alternatives remain, including if the migration/online workflow is unavailable.
2. User enters their current password, exact `DELETE MY ACCOUNT` phrase and checkbox confirmation. Supabase Auth reauthenticates directly; the application never stores a password in request records/logs. Client checks returned identity; SQL derives ownership only from auth.uid(). A refreshed token's `iat` is insufficient: SQL checks signed password AMR within five minutes AND a live, nonexpired matching auth.sessions row.
3. Transactionally record one open request and audit receipt. Same-account retries/double taps return the same request; an interrupted response can be recovered by reading own status/retrying. No profile, listing, file or report is deleted/anonymised at submission.
4. Owner reads status/public message and can withdraw pending/in-review/on-hold requests after reauthentication. After approval, contact support. Other users cannot read or withdraw the request; clients cannot set review status or mark completion.
5. Restricted administrator queue shows requests and a read-only inventory (active listings, unresolved reports, vendor-prefix files including orphan uploads, DB paths and thumbnails). Explain retention/holds to the user and record in-review/on-hold/approved-for-erasure with version-checked audit events. Stale double decisions fail. Inventory is a point-in-time review aid, not a deletion manifest or authority to remove shared content.
6. **No permanent executor exists and no “completed/deleted” status is exposed.** Approval means ready for a separate controlled operation. Until then accounts remain usable; this is explicitly stated. Do not claim that sessions are revoked or Storage is erased by a request.

## Permanent erasure runbook — release blocker, not an executable production script

The lack of a verified production database AND Storage backup makes immediate automated erasure unsafe. No deletion worker, cron, scheduled purge, Auth Admin endpoint or service-role deployment is activated in this PR. This deliberately follows the request-and-review alternative. Before implementing/authorising erasure:

- Verify a recoverable database backup and separate Storage backup; approve retention schedule and specific holds. Resolve seller/listing/dispute impact without forcing unnecessary retention. Copy only specifically necessary evidence into a restricted, access-audited case store with review/expiry and no public URL.
- Maintain a restricted durable job journal: request ID, approved scope, backup/hold evidence references, object manifest/checksums, per-object outcomes and phase/checkpoint IDs. Never log passwords, tokens or broad profile dumps. Take a final inventory after preventing new writes; include legacy DB references, thumbnails/originals, unreferenced prefix uploads, shared object references, provider/CDN caches and relevant reports/rankings. A stale earlier inventory cannot authorise erasure.
- First disable sign-in and revoke all sessions/refresh tokens using approved server-side Auth tooling. Test replay of already-issued access tokens against sensitive database AND Storage reads/writes. Supabase access tokens may survive sign-out/user deletion until expiry; a mere sign-out is insufficient. Add/rehearse a durable account lock/tombstone and checked policies/entrypoints where needed. Do not proceed or label deletion complete until stale-token access is denied. No such universal lock is claimed implemented here.
- Remove public exposure and erase approved Storage objects via the supported Storage API, never DELETE storage.objects SQL. Detect shared references first. Journal each successful object deletion; retries must tolerate missing objects. Verify recursive listing/reference absence and cache-removal arrangements. Handle shared events/promotions by redaction/reassignment rather than deleting unrelated content.
- Erase/minimise personal text in comments/reports/snapshots/rankings and separately retained evidence according to approved scope; SET NULL alone is not anonymisation. Remove owned relational records/Auth user only once the file manifest and justified retained evidence are safe. Cascades must be rehearsed against realistic synthetic fixtures and constraints before execution.
- A crash resumes from the last verified checkpoint: do not restore a partially erased account's public data to make it “whole.” Keep the account restricted while retrying. Escalate unexpected FK/file/provider failures; preserve a minimal receipt of scope/outcome. Verify all provider/API paths and clean device/session state where controllable.
- Only a separately reviewed finalisation mechanism may record verified completion after all assertions pass, with the user's explanation of retained categories and backup expiry. Actual erasure, full storage cleanup, token replay denial after deletion, anonymisation and failure recovery remain unimplemented/unverified release gates. Never test them on real users.

## Security and privacy assessment

New risks: rights-request records and inventory reveal account ownership/vendor paths, so restrict to owner/admin as appropriate; internal audit history is admin-only. Review explanations visible to the requester must not leak another party's details. Do not make requesting deletion conditional on disclosing a reason, supplying extra documents upfront, paying, or resolving every dispute. Holds need a specific necessity and review date; administrators must not treat “approved” as authority to bypass production approval/backups.

The user-facing policy pages describe providers, device storage, public/private image behavior, raw analytics, private matric handling, legal grounds proposed for review, rights/complaints and the actual request workflow. Draft status, minors/capacity arrangements, legal operator/registration and provider-transfer decisions remain explicit. There is no claim that proposed retention durations are active or legally mandated.
