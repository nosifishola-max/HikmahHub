## Changes

- Put the homepage hero/search before promotions. Keep promo art uncropped, with descriptive copy below rather than obscuring artwork. Make marketplace filters compact, expose readable availability, improve empty copy, focus rings, reduced motion, and six-item mobile navigation (previous grid had five columns).
- Vendor listings become stacked mobile rows without losing edit, submit, delete, availability, pending-change and rejection/review history flows. Failed availability changes restore the previous value.
- Sticky product contact controls sit above mobile navigation and preserve immediate WhatsApp opening and click tracking. Sold/unavailable products invite an availability enquiry.
- Add event likes, server-derived first-name comments, event/comment reports, and reported-comment context in the existing admin report queue. Resolve-and-hide hides the comment and keeps audit logging. Discussion fails gracefully before the database migration exists. No profile identifiers or like user lists are exposed by the new UI/API.
- Require matric number, faculty and department for new/rejected vendor applications. Normalize matric case and whitespace in the UI and database trigger; an expression unique index also covers pre-existing differently formatted values without rewriting them. Matric stays in profiles with existing owner/admin RLS. Approved vendors keep dashboard access without reapplying.

## Analytics investigation (read-only, 2026-10-25 UTC)

All four production tables (`product_views`, `store_views`, `whatsapp_clicks`, `searches`) had zero rows. The last-24-hour edge-log message search found zero analytics RPC entries; this is supporting evidence, not proof of absence in every log field.

The browser discarded lazy Supabase/PostgREST builders at every tracking call. Creating a builder does not send an HTTP request: consuming its promise does. The shared `recordAnalytics` helper now awaits each RPC and handles failures without blocking navigation/contact. Tests use actual lazy thenables and verify all four event names execute once, and failures omit sensitive payloads from logs. Search tracking remains once per real initial fetch, with existing server restrictions (signed in, query >=2 characters). View RPCs allow anonymous views; search/click RPCs require sign in. No synthetic production events were inserted. Runtime collection still needs an approved post-release check.

## Security review

Reviewed existing RLS, analytics RPC definitions, profile role guard, report resolver, preview view definitions, and security advisor output.

- `public_product_previews` and `public_vendor_previews` deliberately bypass underlying signed-in-only table policies to show limited approved/featured records to visitors. Their allowlisted columns contain no matric or other private profile data. Blindly setting `security_invoker=true` would remove anonymous previews. Preserve these reviewed exceptions pending a separately tested redesign.
- Analytics RPCs intentionally write as definer because clients cannot insert directly into the admin-readable analytics tables. They use an empty search path, derive user IDs from `auth.uid()`, and validate approved targets. Do not change them to invoker just to clear advisor warnings.
- New aggregate/comment RPCs explicitly require sign in and a published event, have an empty search path, and revoke PUBLIC/anon execution. They expose no arbitrary caller-selected user identity. New tables enable RLS, and comments expose only selected columns.
- Existing `is_admin()` checks private database profile role; a profile trigger prevents self-changing role/active state. Existing admin resolver checks it before writes. Its anonymous/PUBLIC execution is revoked in the draft.
- Advisor warnings include other security-definer RPCs and disabled leaked-password protection. A complete audit of those other RPCs and Auth configuration remains outstanding; no blanket privilege change was made. See [Supabase advisor guidance](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable) and [password protection](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection).

## Migration and validation

`db/v1_1.sql` is a transactional, unapplied migration draft against the existing schema. It does not delete or backfill production rows. `scripts/prepare-migration.sh` uses `supabase migration new` to generate the timestamped migration and copies the draft into it; it never links or pushes. The CLI is unavailable in this workspace, so no timestamped migration/history entry was fabricated.

Before any application:

1. Obtain explicit owner approval for any production database write and separately for production deployment. Do not run production `db reset`, seed scripts or write tests.
2. Restore an authorized schema snapshot into a disposable local database. The repository currently has no base schema/migration history. Do not create a new hosted project or paid staging.
3. Recheck normalized matric duplicates using an aggregate query (0 duplicate groups observed during this review). If duplicates appear, stop and review with the owner; never delete or silently merge users.
4. Generate a migration locally, apply to that disposable database, and run `psql -v ON_ERROR_STOP=1 -f tests/database-contract.sql` there. Validate SQL compatibility and role scenarios below before approving production use. New definer RPCs intentionally remain advisor exceptions; verify their guards/grants.
5. Rehearse application/rollback with a backup and record the original resolver definition, grants, schema and migration history. Set appropriate lock/statement timeouts for the unique index on the actual database size.

## Rollback

Prefer rolling back application code to the pre-v1.1 commit while retaining new database tables/data and compatible RPCs. Do not drop comments, likes, reports, profiles, or analytics to roll back the UI. Existing reports with `event_comment` targets mean the target constraint must remain compatible. If vendor validation causes an incident, an explicitly approved follow-up migration can disable/drop only `require_vendor_identity` and `normalize_profile_matric` triggers; retain profiles and uniqueness protection unless separately reviewed. Restore the prior resolver only after accounting for new comment reports, or keep the backward-compatible extension. Any database rollback needs explicit approval and a tested backup/recovery plan.
